# MemoryAnchor 评测协议

**要回答的问题**：让模型在一个陌生仓库里修 bug、加功能时，MemoryAnchor 记下的项目知识，能不能让它**不破坏那些代码里看不出来的预期行为**，同时还能把任务做完、成本可接受。

## 1. 核心设计：隐藏不变量

1. 选一个测试全部通过的仓库。
2. 挑出一批**预期行为（不变量）**：只写在犄角旮旯的文档里，或者干脆没写，只体现在测试里。
3. 把检查这些行为的测试**藏起来**（agent 看不到、跑不了），评分时再放回去。
4. 把这些行为写成 MemoryAnchor 记忆：guardrails / decisions / project-state，**一条一行**，写法和真实使用时一样。
5. 让模型修 bug 或开发功能，最后跑隐藏测试，看它有没有破坏预期行为。

## 2. 对照组

每组都模拟一种真实的仓库状态。项目知识总量相同，区别只在于知识放在哪里：

| 组 | `AGENTS.md` | 不变量规则在哪里 | 回答的问题 | 默认跑 |
|---|---|---|---|---|
| `off` | 400–500 行“裸”版本，删掉了不变量相关的行 | 只在仓库原有的位置（犄角旮旯文档，或无处可查） | 下限：没人写下来时破坏多少 | ✓ |
| `scattered` | 同 `off` | 散落在仓库各处的小文档里（`NOTES.md`、`docs/*.md`、模块 README），每条埋在一篇讲相关话题的笔记中间 | 现状：知识写下来了，但要模型自己去找 | ✓ |
| `doc` | 400–500 行，所有规则、决策、模块说明都堆在里面 | 混在大文档中间，每轮都在 system prompt 里 | 上限参考：等于强制模型全读一遍 | 仅特殊需要 |
| `ma`  | 压缩后的版本（约 135 行，再加 `anchor init` 追加的规则段） | `.memoryanchor/` 里的 guardrails / decisions / project-state，开 `--ma` | 用 MemoryAnchor 管理同样的知识，效果如何 | ✓ |

模型、prompt、工具、`maxTurns` 各组完全一样。

`ma` 胜过 `off` 几乎是必然的，因为它直接拿到了答案。真正能证明 MemoryAnchor 价值的是 **`ma` vs `scattered`**：知识内容相同，比的是“散落在仓库里、靠模型自己找”和“MemoryAnchor 集中存放并主动注入”这两种真实做法。`doc` 把全部知识塞进每轮的 system prompt，几乎等于逼模型看一遍，只作为上限参考，用 `--groups off,scattered,doc,ma` 显式开启。

所有组的知识都由同一份记忆文件生成：通用说明 + 全部 guardrails + decisions + 模块状态。`off` 是从大 `AGENTS.md` 中删掉所有暴露不变量的行；`scattered` 在 `off` 的基础上，把同样的知识按话题拆成小文档放回仓库。规则行必须在文档中间（不在前后 20%），避免注意力天然落在开头或结尾。

## 3. 任务

每个任务包含：

- **任务描述**：修一个 bug 或加一个功能。
- **可见测试**：正常的测试，agent 可以运行。
- **FAIL_TO_PASS**：验证任务本身完成了。
- **隐藏不变量测试**：每条测试标注它对应哪条规则。
- **两个参考答案**：
  - **正确解**：完成任务，且所有测试通过。
  - **陷阱解**：最直接、最“顺手”的写法。它能完成任务，但会破坏至少一条不变量。

**陷阱解是关键，而且要显眼。** 强模型会照着现有代码的写法做，所以陷阱最好就是代码里现成的东西：一个现成的 helper、一段可以照抄的相邻实现。 如果“顺手”的写法本来就不会碰到某条不变量，那条不变量就测不出任何区别，不进评测集。入库前要验证：正确解全部通过，陷阱解在隐藏测试上失败。

**off 必须踩。** 入库前先只跑 `off` 组（`--groups off`）。`off` 没有破坏不变量，说明这条规则就是模型的默认行为，或者能从代码直接推出来（比如 schema 里就看得出两类设置共用一行），这样的规则测不出知识的作用，必须换掉。代码里能看出来的规则可以留作对照，但每个任务至少要有一条 `off` 稳定会破坏的不变量。

**规则要是“只有项目内部才知道的事实”。** 细心的工程师自己就会想到的规则（按惯例排序、照着周围代码校验、考虑重名账号），`off` 也能做对，测不出知识的作用。有效的是业务约定（保留用户名、最低年龄、默认币对排最前）、数据事实（存在 4 个字母的 `USDT`、盘中会写入当天行）、反直觉的历史决定（周末不补点）。“顺手写法”的陷阱，敌不过周围代码里更强的惯例。

**记忆要像真实使用。** guardrails 里同时放入大量与当前任务无关的规则（总量接近 MemoryAnchor 的建议上限），而且规则要写成约束，不要照抄测试断言。否则测的是“抄答案”，不是“记得项目约束”。

**规则不要和任务冲突。** 任务要求改变的行为，不能同时作为不变量。

**仓库最好冷门，或改用自编的行为。** 如果模型训练时见过这个仓库，`off` 组也可能“凭记忆”答对。

起步规模：1–2 个仓库，20–30 个任务，任务以修 bug 和加功能各占一半为宜。

## 4. 每次运行（trial）

1. 从任务快照复制一个全新目录，删掉隐藏测试，`git commit` 作为基线。
2. 放入对应分组的大 `AGENTS.md`；`ma` 组再运行 `anchor init` 并写入记忆。这一步不计入成本。
3. 运行 agent。
4. 评分时，把所有测试文件还原成原版，再放回隐藏测试。agent 对原有测试的改动会被记录，但不扣分：还原后改动影响不了评分，而往已有测试类里加测试本来就是好习惯。
5. 跑全部测试，保存 `result.json` 和 diff。

每个任务、每个组跑 **k = 1 次**。

## 5. 指标

只看结果，不看过程。

| 指标 | 定义 | 地位 |
|---|---|---|
| **完好解决率** | FAIL_TO_PASS 通过、可见测试通过、隐藏不变量测试也全部通过 | **主指标** |
| **不变量破坏率** | 该任务涉及的隐藏不变量测试中失败的比例，**只在任务完成的运行里计算**（没做任务的运行碰不到不变量，算进来会显得虚假安全） | **主指标**（越低越好） |
| 任务完成率 | 只看 FAIL_TO_PASS 是否通过 | 次要：确认 MemoryAnchor 不会让模型变得“不敢动” |
| 稳定性 pass^3 | 3 次运行全部完好解决的任务占比 | 次要 |
| 成本 | 总 token、工具调用数、耗时，以及每个完好解决的任务花了多少 token | 次要，必报 |
| 规则命中 | 失败的运行里，agent 有没有读到（或被注入）对应规则 | 诊断：区分“没看到”和“看到了但没遵守” |

`max_turns`、超时、模型拒答都算失败，不剔除。只有基础设施错误允许重跑，并记录在案。

## 6. 怎么判定有效

- 按任务**配对**：每个任务算 `ma − scattered` 和 `ma − off` 的差值，再对所有任务取平均，并对任务做 bootstrap，给出 **95% 置信区间**。
- **`ma − scattered` 的完好解决率提升显著**（区间不含 0），才能说 MemoryAnchor 比普通文档有用。
- 不变量破坏率下降、但任务完成率也明显下降，说明模型被规则吓住了。这不算赢。
- 成本涨了、效果却没有显著提升，就写“不划算”。

## 7. 报告格式（数字仅为示意）

```
              完好解决   破坏率   任务完成   pass^3   tokens/完好解决
off           30%        45%      80%        15%      250k
scattered     40%        33%      79%        22%      270k
ma            58%        15%      79%        38%      240k
ma−scattered  +18 [+6,+30]   −18 [..]
```

最后人工抽读几份失败的 transcript，确认失败原因在 agent，而不是测试或规则写错了。
